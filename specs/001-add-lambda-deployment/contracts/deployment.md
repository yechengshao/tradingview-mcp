# Contract: Lambda Build, Deployment, and Verification Operations

**Profile revision — 2026-11-03**: The user selected REST API with native usage plans. The [REST service handoff](rest-migration.md) governs the new target and supersedes any HTTP-only exclusion below for future work. Existing HTTP API v2/`$default`/payload2.0 routes, commands and report-v1 details below describe the delivered **legacy HTTP profile**, not an implemented REST deployment. New service-only runtime/report-v2 work is pending; spec 002 owns all new REST attachments and invoke permissions.

This service contract covers delivered ECR/runtime interfaces and planned service publishing-IAM follow-up. [Spec 002](../../../../mcp-auth-subscriptions/specs/002-authentication-api-access/spec.md) owns access infrastructure; [spec 003](../../../../mcp-auth-subscriptions/specs/003-billing-subscriptions/spec.md) owns billing Lambda/DynamoDB. The MCP service contains neither identity nor billing logic.

## Compatibility baseline and verifier dependency policy

Freeze the full pre-feature baseline_ref before implementation changes and capture expectations into the planned `tests/integration/support/baseline.json` from an isolated checkout/archive. Tool catalog, original launch/health contract, and original publishing rules are immutable comparison inputs; candidate source cannot regenerate its own expected values. Baseline images must be built from that pinned revision. Missing baseline source/provenance is a configuration/evidence error.

The existing Python 3.10–3.13 default unit workflow remains usable with its normal development dependencies. Verifier AWS/lint imports must be lazy so importing the CLI or exercising pure report/combine semantics needs no optional AWS SDK. Planned `.github/workflows/test-lambda.yml` runs on push/PR using Python 3.11, ensures the pinned baseline revision is available, installs `uv sync --dev --group deployment --locked`, and runs the selected hermetic report/infrastructure/verifier tests plus template/schema linting. Missing dependencies or selected tests fail that job rather than becoming silent skips. Native container/publishing gates remain separately explicit; no test CI cloud credentials or mutations are required.

## Artifact build and publication

- `Dockerfile.lambda` uses an isolated Lambda entrypoint; its Dockerfile-specific ignore file allowlists `pyproject.toml`, `uv.lock`, `README.md`, `src/`, and the Lambda Dockerfile. Exclude credentials, `.aws`, `.env`, `.codex`, `.agents`, and tests.
- Build arguments SOURCE_COMMIT/LOCK_SHA256 become release labels. Build linux/arm64 with adapter 1.1.0, uv 0.13.1, locked noneditable production dependencies, and no provenance/SBOM attachment index.
- Build once with `--load`, test locally, then push that image to ECR. The manifest config.digest must match the tested local image ID. Record immutable manifest digest; reject indexes/wrong architecture.
- Runtime: port 8000, buffered JSON, strict 200 readiness on `/health`, writable `/tmp`, non-root-readable/executable packages. Local startup requires no AWS credentials or authentication credential. Supply the nonsecret expected public authority in TRADINGVIEW_MCP_PUBLIC_HOST for transport-security tests; no cloud credential or provider lookup is required.

## Supplied gateway prerequisites

The initial integration profile is an existing HTTP API v2 in the same account/region, enabled default execute-api endpoint, existing `$default` stage with AutoDeploy true, and an existing REQUEST custom authorizer backed by the owner's Cognito policy. Supply ApiId/AuthorizerId and credential acquisition/refresh instructions. The authorizer must already have correct invocation permission, Authorization-header identity input, policy/cache behavior for all feature routes, and sanitized correlation logs available for verification.

This service feature does not provision or modify API/stage/Cognito/authorizer or billing resources. Sibling spec 002 provides the access identifiers; its provisioning/adoption contract is independent. Named stages, REST APIs, and custom-domain mappings are outside this initial profile. Preflight rejects incompatible resources and conflicting exact/method-specific `/mcp`, `/mcp/`, or `/health` routes; existing routes are not adopted/overwritten. The owner reserves these paths across the API's stages. Other stages must not invoke the alias: backend permissions cover `$default` only.

## ECR bootstrap: `infra/lambda/ecr.yaml`

Input RepositoryName. Create/tag one private immutable-tag ECR repository with scanning, encryption, explicit project/feature/stack ownership, and a Lambda pull policy limited to repository/account/region (BatchGetImage/GetDownloadUrlForLayer). Output RepositoryUri/RepositoryName. Retain the repository on deletion/replacement; pruning images or deleting it is a separate explicit cleanup action after runtime removal. Preserve rollback images until no longer needed.

## Runtime: `infra/lambda/runtime.yaml`

Parameters: ImageUri, DeploymentRevision, SourceCommit, LockSha256, ApiId, AuthorizerId, sizing/retention parameters, and optional RollbackVersion; validation/defaults are in [data-model.md](../data-model.md). MarketauxApiToken/ProxyUsernamePrefix/ProxyPassword (optional NoEcho strings) and ordinary application settings are defined below. No MCP authentication-token/digest parameter is introduced.

Resources:

1. Explicit `/aws/lambda/<runtime-stack-name>` log group.
2. Lambda execution role with only CreateLogStream/PutLogEvents on the declared log-group streams; no provider configuration-store read/decryption or other application AWS API access.
3. Image function named for the validated stack (at most 48 characters), arm64, exact ECR digest, no VPC attachment, defined environment/sizing.
4. Published version tied to DeploymentRevision; retain replaced versions.
5. Stable `live` alias selecting the candidate or a validated retained RollbackVersion of this function.
6. Feature-owned `AWS::ApiGatewayV2::Integration` referencing supplied ApiId, IntegrationType AWS_PROXY, IntegrationMethod POST, alias invocation URI, PayloadFormatVersion `2.0`, TimeoutInMillis 30000. Use direct Lambda invocation; no Function URL.
7. Three feature-owned routes in supplied ApiId: `ANY /mcp`, `ANY /mcp/`, `GET /health`. All use CUSTOM plus supplied AuthorizerId and target the integration.
8. Alias-scoped Lambda permissions: principal `apigateway.amazonaws.com`, action `lambda:InvokeFunction`, deployment SourceAccount, SourceArn restricted to that API and `$default` stage. Separate method/path patterns cover `*/mcp`, `*/mcp/`, and `GET/health`; no wildcard API/stage or public principal. Ensure permissions exist before routes become callable; verify final deployed configuration.

Do not create API/stage/authorizer/Cognito resources or change the shared stage's deployment settings. ApiEndpoint is read/validated from the supplied API and is `https://<ApiId>.execute-api.<region>.amazonaws.com` for this profile. Outputs: ApiId, ApiEndpoint, ApiStageName (`$default`), AuthorizerId, IntegrationId, McpRouteId, McpSlashRouteId, HealthRouteId, McpEndpoint, HealthUrl, FunctionArn, AliasArn, PublishedVersion, ActiveVersion, ImageUri, SourceCommit, LockSha256, DeploymentRevision, LogGroupName. No credential, token digest, or FunctionUrl output.

Defaults: memory 1024 MiB, Lambda timeout 25 seconds (1–25), temporary storage 512 MiB, reserved concurrency five, logs 14 days. Gateway timeout 30 seconds, client response deadline 35 seconds, connection limit 10 seconds; initialization shares gateway time. Preflight concurrency quota and same-account/same-region image/API/function. Do not silently remove a reservation cap.

## Native application environment contract

All nine `.env.example` keys are native Lambda Environment.Variables; the authoritative matrix is in [data-model.md](../data-model.md). The template merges these values with adapter/public-host/release settings in the complete environment map. Lambda supplies the values before startup; existing service code reads them normally. No entrypoint/startup retrieval hook, SDK addition, external configuration-store resource, or extra runtime permission is required. `.env` files and credentials are excluded from the image/build context.

Ordinary deployment inputs: MarketauxDailyBudget → MARKETAUX_DAILY_BUDGET (`90`); ProxyEnabled → PROXY_ENABLED (`true`); ProxyHost → PROXY_HOST (`p.webshare.io`); ProxyPort → PROXY_PORT (`80`); ProxySessionMin → PROXY_SESSION_MIN (`1`); ProxySessionMax → PROXY_SESSION_MAX (`250`). Validate nonnegative budget, literal booleans, hostname/port, and positive ordered session bounds. The daily news budget remains process-local, not a shared daily quota.

Sensitive inputs: MarketauxApiToken → MARKETAUX_API_TOKEN; ProxyUsernamePrefix → PROXY_USERNAME_PREFIX; ProxyPassword → PROXY_PASSWORD. All three are String parameters with NoEcho true and default empty. Empty optional credentials preserve the current news/proxy fallback. These are upstream provider credentials, not incoming MCP client tokens. No credentials are returned as stack outputs or included in metadata, labels, names, URLs, logs, or report evidence.

Use the CloudFormation parameter UI or a private mode-0600 JSON input file outside the checkout, build context, and verification evidence directory. The CLI accepts `--parameter-overrides file://<absolute-path>` with ParameterKey/ParameterValue objects; avoid raw credentials in command arguments and disable shell/CLI debug tracing. Do not print or retain temporary credential files in artifacts. NoEcho masks stack parameter displays, not arbitrary metadata/outputs or Lambda configuration reads; scope configuration access and redact full environment responses. This phase intentionally stores provider values in native Lambda configuration and requires no separate retrieval mechanism.

All configured entries share the Lambda 4-KB quota, including provider credentials and platform-adapter/release variables. Values are literal NUL-free strings, not shell-expanded expressions. Update the full intended map through CloudFormation, preserving unchanged values; do not overwrite required adapter keys or create manual drift. Invalid ranges/size cause redacted configuration diagnostics. Readiness must not query configuration stores or market providers.

Each published function version snapshots its environment values. Credential or ordinary-setting updates require a fresh DeploymentRevision, function environment update, publication, and verification; no image rebuild. Alias rollback restores the older values, which may no longer be valid upstream. If credentials have expired/revoked, publish a forward update using the known-good image and current values. This lifecycle is separate from external Cognito/MCP client authorization, which is not rolled back by the service. Cleanup removes only project-owned runtime/integration resources and temporary input files; no external provider account or authorization resource is modified.

## Lifecycle and ownership

Bootstrap ECR → build/test/publish image → deploy runtime and feature attachments → observe alias/gateway configuration → verify. Update using immutable digest and fresh DeploymentRevision; application-environment changes also publish a version. Rollback through CloudFormation RollbackVersion with other parameters preserved. Forward deployment explicitly clears RollbackVersion; rollback preserves DeploymentRevision. Record prior version/digest before updates. MCP client token renewal/rotation/revocation belongs externally and does not republish the service; application rollback does not change supplied Cognito authorization policy/client credentials. Provider credential rotation follows the native environment publication workflow above.

Runtime removal deletes only feature-created routes, integration, alias permissions, versions/function, and declared runtime resources. Verify route removal has reached the auto-deploy stage and no feature attachment remains; preserve the supplied API/stage/authorizer/Cognito and unrelated routes. ECR retention is intentional. Inspect the named repository's ownership/content before explicit purge/removal; never use account-wide wildcard cleanup. Lifecycle evidence records supplied infrastructure preservation.

## Verification CLI: `scripts/verify_lambda.py`

- `local --baseline-image IMAGE --lambda-image IMAGE --report PATH`: existing Docker/stdio/unit checks, Lambda image/storage, full catalog parity, controlled provider success/error, invalid tool input, authority/origin/method/slash checks, and provider-independent health. Demonstrate no MCP client-authentication credential requirement. Use synthetic environment values to cover all nine mappings/defaults, optional fallback, invalid setting/size diagnostics, and redaction; never use production provider credentials in local fixtures. Manage only this run's temporary loopback containers/processes. Emit all stages, but authorization and cloud-only stages are not_run.
- `live --region REGION --stack NAME --expected-image-uri URI --report PATH [--additional-stack NAME ...]`: AWS reads plus MCP HTTP calls, never infrastructure mutation. Resolve active version/digest and gateway outputs from named stacks. Read allowlisted nonsecret application settings and the active configuration revision; never dump full Lambda Environment responses or resolved secret values. Bind additional targets to the same intended provider configuration/revision and matching nonsecret settings, allowing distinct gateway/public-host identifiers. Read API/stage/routes/integration/authorizer configuration, function/alias policies, absence of Function URLs, and gateway/Lambda correlation evidence. Confirm all three feature routes are CUSTOM and point to the expected authorizer/integration/alias. Run missing/invalid credential checks: require 401/403 before service invocation, with gateway request IDs and sanitized evidence. A configuration 500 is a failed check. Check every feature route and public bypass exposure; do not treat local auth-free behavior as public authorization evidence. With a valid externally issued credential, run at least 20 complete interactions using futures_watchlist, five concurrent clients, and ten health checks; observe two fresh environments. Additional cold-evidence stacks require the same release/application settings and separate supplied compatible APIs/authorizers; verify each target's security independently.
- `combine --local-report PATH --live-report PATH --lifecycle-evidence PATH --report PATH`: merge compatible evidence for the same release; validate schema and cross-field provenance; calculate success without turning missing/failed stages into passes. Lifecycle evidence follows `$defs.lifecycleEvidence`: reviewer/time, starting/updated/rollback image URIs, target stack IDs, and deploy/update/rollback/cleanup/documentation steps with sanitized refs. Starting and rollback image URIs equal the final expected/resolved release; updated URI identifies a different tested release. Walkthrough stack IDs must be a subset of reported targets. Every lifecycle step must pass, including environment-only configuration update/rollback coverage and preservation of supplied infrastructure after cleanup.

The live verifier must not output provider values; inspect nonsecret configuration/revision fields and sanitized evidence only. MCP client credentials: live mode reads an externally issued client credential from TRADINGVIEW_MCP_TOKEN, used only in the Authorization header expected by the supplied authorizer. There is no token command-line option and no token generation service. Refresh through the supplied Cognito flow before expiry. AWS observations use the normal credential chain in the optional deployment-tools environment. Live mode never mutates IAM, gateway, Cognito, authorizer, function configuration, stack, alias, ECR, or logs. Provider settings/credentials use the separate deployment inputs above and must not be confused with TRADINGVIEW_MCP_TOKEN. Logs and report evidence must not reveal raw provider values, provider-value hashes, full resolved environment maps, client credentials, or claims; adapter DEBUG/header logging is disabled.

Exit codes: 0 full success; 1 attempted acceptance failure; 2 incomplete/not_run without failed checks; 3 invalid arguments/configuration, malformed evidence, or provenance mismatch. Local-only normally exits 2. A missing valid external credential makes dependent live stages not_run; it is not proof of authorization success.

Required stages remain artifact_startup, health, client_initialization, tool_discovery, tool_execution, authorization, invalid_tool_input, upstream_failure, cold_start, concurrent_clients, docker_compatibility, local_transport_compatibility, existing_unit_suite, release_identity, release_lifecycle, documentation_walkthrough. Optional live_market_probe records provider availability separately. Complete tool verification includes initialized notifications, pagination, and controlled errors.

## Report semantic validation

The schema remains version 1 and requires nullable target.gateway and authorization_evidence fields. Local target.gateway/authorization_evidence are null. A live target's gateway records api_id, stage_name (`$default`), authorizer_id, integration_id, three unique route IDs, and payload format `2.0`. Passing authorization requires missing/invalid credential denials (optional expired), gateway IDs, service_invoked false, configuration evidence, and public_bypass_absent true. Semantic validation resolves route IDs to the required keys, checks CUSTOM/authorizer/integration/alias/permission configuration, binds endpoint to supplied API, and correlates requests to evidence of no service invocation. A status code or absent application log alone is insufficient. Additional targets need their own configuration/denial evidence, referenced by authorization-stage evidence.

Also enforce expected/resolved URI equality, local config digest versus registry config digest, matching source/lock identity, passed counts not exceeding attempted counts, and zero failed primary interactions for full success. Cold-start pass requires at least two distinct function/version/log-stream environments with platform request and initialization evidence for the same release, and each counted startup request must join through gateway/integration evidence to a request belonging to a successfully completed initialization/discovery/tool interaction in this run. Initialization or discovery may be the cold request; no cold tool-call-only requirement is imposed. Emit completed-interactions.json with sanitized interaction_id/completed_success and per-MCP-stage gateway/platform request IDs, function/version/log-stream identity, observed time, and correlation references; bind it through existing stage evidence ref/SHA-256. Derive evidenced_fresh_starts from distinct qualified joins. Health-only, failed/incomplete, wrong-release/time-window, or unmatched request evidence cannot count; missing links keep cold_start not_run. Raw startup count, sessions, and idle delays do not prove this acceptance criterion. Bind lifecycle and all target/release evidence to this run. Structural JSON Schema validation cannot replace these cross-field/control-plane checks.
